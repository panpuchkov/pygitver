# Conventional Commits as the commit standard

- Status: Accepted
- Date: 2026-05-06

## Context and Problem Statement

The tool needs a deterministic way to derive a release version and a grouped
changelog from a range of git history. Free-form commit messages cannot be
parsed reliably enough to drive release automation: humans phrase the same
intent in many ways, and there is no signal for "this is a breaking change"
short of reading the diff.

We need a commit-message convention that authors find tolerable, that
machines can parse without natural language understanding, and that already
has industry traction so contributors do not need to learn yet another
project-local rule.

## Decision Drivers

- Commit messages must be the single input to bump rules and changelog
  generation — no parallel "release notes" file.
- Authors must not need a special tool to produce a valid commit; plain
  `git commit -m` must work.
- Breaking changes must be flagged at commit time, not discovered during
  release.
- The convention must already be familiar to a meaningful share of
  contributors.

## Considered Options

- Conventional Commits 1.0 (full spec).
- Conventional Commits 1.0, simplified subset.
- gitmoji or another emoji-prefix scheme.
- Project-custom prefixes (e.g., `[FEAT]`, `[BUGFIX]`).
- No convention; infer everything from issue/PR labels.

## Decision Outcome

Chosen: **Conventional Commits 1.0, simplified subset**.

The accepted commit grammar is:

```
<type>[optional scope]: <description>
```

Recognized types: `fix`, `feat`, `build`, `chore`, `ci`, `docs`, `style`,
`refactor`, `perf`, `test`, `deprecated`, plus the literal `BREAKING CHANGE`
as a synonymous header for major bumps. A trailing `!` after the type or
scope marks a breaking change. The scope, when present, is enclosed in
parentheses and may not contain a colon or closing parenthesis.

Two carve-outs are tolerated to avoid friction with default git workflows:

- `Merge branch ...` — auto-generated by `git merge`.
- `Merge pull request ...` — auto-generated by GitHub PR merges.

These are recognized but contribute nothing to the changelog or bump rules,
because changelog ranges are computed with `--no-merges`.

Any commit that does not match the grammar above and is not one of the merge
carve-outs is a *non-conventional commit*. Such commits do not block the
linter when checked outside the hook, but the commit-msg git hook (see
ADR-0005) rejects them at commit time. In a changelog they are surfaced
under a `non_conventional_commit` group and contribute a `patch` bump.

### Consequences

- Good: bump rules and changelog grouping become a pure function of the
  commit log over a range — reproducible, no out-of-band state.
- Good: contributors who already know Conventional Commits transfer their
  habits in directly.
- Good: breaking changes are explicit at the moment of commit (`!` or
  `BREAKING CHANGE`), not discovered later by a human reviewer.
- Bad: the convention must be enforced; a single non-conventional commit
  silently rolls into a `patch` bump rather than the type the author
  intended. Mitigation: the commit-msg hook (ADR-0005) blocks invalid
  messages locally before they reach the repo.
- Bad: the type list is fixed in code; adding a new type requires a code
  change and a release. Acceptable because the spec's list is stable.

## Pros and Cons of the Options

### Conventional Commits 1.0 (full spec)

- Good: well-known, has tooling, covers footers and references.
- Bad: full footer parsing (e.g., `Refs:`, `Co-authored-by:`) is not needed
  for bump or changelog generation; supporting it would add code without
  user-visible benefit.

### Conventional Commits 1.0, simplified subset

- Good: same author-facing experience as full spec — authors do not have
  to learn anything different.
- Good: implementation surface is small; the parser is a single regex.
- Bad: footers like `BREAKING CHANGE: ...` in the body are detected
  textually rather than parsed structurally. Acceptable: the textual
  detection covers the only case that matters (whether the commit triggers
  a major bump).

### gitmoji / emoji prefixes

- Good: visually distinctive in `git log`.
- Bad: less portable across terminals, IDEs, and PR review tools; less
  recognizable to contributors outside the convention's user base.

### Project-custom prefixes

- Bad: zero ecosystem support; new contributors must learn a project-local
  rule that does not transfer elsewhere.

### No convention; infer from labels

- Bad: requires a forge that supports labels, ties releases to a specific
  hosting platform, and moves the source of truth out of the git history
  into per-PR metadata that is fragile and forge-specific.
